Follow-up review: taus.py / scalefactors.py tau ID+ES producer call signatures
================================================================================
Scope: closes AUDIT_REPORT_tau.txt's explicitly stated gap -- "did not
exhaustively re-verify every one of the ~15 SF/ES producer overloads in
taus.py/scalefactors.py against every era's json". Covers:
  - producers/taus.py (all producer/ProducerGroup definitions)
  - producers/scalefactors.py's tau vsJet/vsEle/vsMu ID SF producers and
    tau energy-scale-related producers
Out of scope (owned by parallel agents, not touched, not edited):
  - tau_triggersetup.py
  - trigger-SF producers in scalefactors.py (SingleEleTriggerSF,
    SingleMuTriggerSF, MuTauTriggerLeg1/2SF, EleTauTriggerLeg1/2SF,
    DoubleTauTriggerLeg1/2SF)
  - config.py (read-only reference only)
  - producers/met.py

METHOD
------
For every Producer/ExtendedVectorProducer call string in producers/taus.py
and producers/scalefactors.py (tau-ID/ES portion), matched the Python
`call=` argument list one-for-one against the actual C++ function overload
it invokes, using include/taus.hxx (declarations) and src/taus.cxx
(implementations, read-only, outer CROWN repo) as ground truth. Where the
implementation calls correctionlib's `evaluate()` directly, additionally
cross-checked the literal positional order of that evaluate() call against
the real `inputs` list of the deployed correctionlib json (inspected
directly via gzip+json.load from /cvmfs/cms-griddata.cern.ch, for both a
pre-2024 era (2022preEE) and 2024), matching the ground-truth technique the
original audit used.

RESULT: no new bugs found in either file.
--------------------------------------------------------------------------

`physicsobject::tau` namespace:
  - TauPtCorrection_eleFake -> PtCorrectionMC_eleFake (4 variation args:
    dm0_barrel, dm1_barrel, dm0_endcap, dm1_endcap) -- matches exactly.
  - TauPtCorrection_muFake -> PtCorrectionMC_muFake (1 variation arg) --
    matches.
  - TauPtCorrection_genTau / TauPtCorrection_genTau_dm_binned ->

    overload -- matches.
  - TauPtCorrection_genTau_dm_pt_binned -> PtCorrectionMC_genuineTau, the
    no-wp/8-variation (dm{0,1,10,11}_pt{20to40,40toInf}) overload --
    matches; argument order dm0,dm1,dm10,dm11 with pt20to40 before
    pt40toInf in each pair, exactly as declared.
  - TauPtCorrection_emb_genTau_dm_binned/_dm_pt_binned ->
    PtCorrectionMC_genuineTau, the wp+vsele_wp overloads (4- and
    8-variation respectively) -- matches; wp/vsele_wp param order
    (id_algorithm, wp, vsele_wp, then variations) is correct.
  - TauPtCorrection_MC_v12 -> PtCorrectionMC, the overload with
    4 DM-binned mufake variations + 4 DM-binned (non-pt) gentau

  - TauPtCorrection_MC -> PtCorrectionMC, the overload with 4 DM-binned

  All decay-mode naming (1prong0pizero=DM0, 1prong1pizero=DM1,

  convention.

GROUND-TRUTH JSON CROSS-CHECK (evaluate() call order vs json `inputs`)
--------------------------------------------------------------------------
Inspected the deployed jsons directly (2022preEE and 2024 tau.json.gz,
gzip+json.load, walking the correction node tree) and compared each
correction's declared `inputs` list against the positional order used in
the corresponding evaluator->evaluate({...}) call in src/taus.cxx
(read-only, outer repo; not edited -- three other agents own C++/other
config areas, this was cross-checked purely as ground truth for judging
the Python-side wiring):
  - DeepTau2018v2p5VSe: json inputs = [eta, dm, genmatch, wp, syst].
    C++ evaluate({abs_eta, decay_mode, gen_match, wp, variation}) --
    order matches exactly.
  - DeepTau2018v2p5VSmu: json inputs = [eta, genmatch, wp, syst]
    (genmatch remapped via a transform node before the wp/eta/syst
    category tree) -- C++ evaluate order (eta, wp-tree traversal, syst)
    is structurally consistent with this input list.
  - DeepTau2018v2p5VSjet: json inputs = [pt, dm, genmatch, wp, wp_VSe,
    syst, flag] for BOTH 2022preEE and 2024 (identical input-list shape
    across the pre-2024/2024+ split already documented in
    AUDIT_REPORT_tau.txt Issue #2). C++ evaluate({pt, decay_mode,
    gen_match, wp, vsele_wp, variation, sf_dependence}) -- order matches
    exactly (wp_VSe<->vsele_wp, syst<->variation, flag<->sf_dependence).
  No mismatches found between the evaluate() call order and the json's
  declared inputs for any of the three corrections checked.
