Shift renaming log
==================
Generated while aligning shift names in config.py, jet_variations.py, and
tau_triggersetup.py with the CMS Common Analysis Tools naming conventions
(Conventions - CMS Common Analysis Tools Documentation) and the master
systematics list (systematics_master.yml), both from
https://cms-analysis.docs.cern.ch/guidelines/systematics/systematics/

Format: original_name -> new_name   [file]   notes

Convention recap: CMS_<type>_<obj>[_<step>][_<extra>][_<era>], type in
{eff, scale, res, trigger/trig, fake}, obj in {e, m, t, j, b, g, met}.
Theory uncertainties use pdf_*, QCDscale_*, ps_isr/ps_fsr, BR_*, UEPS
(not prefixed with CMS_). Names are kept singular/stem-form wherever the
code appends "Up"/"Down" automatically via shift_map; where the code
already bakes "Up"/"Down" into the name explicitly (no shift_map), the
new name keeps that suffix explicit too, matching the original pattern.

=== Summary of edge cases requiring possible follow-up ===
1. ggH/qqH combined QCD scale / PDF / PS weights in config.py: the same
   shift name is applied whether the sample is ggH or qqH. Consider
   whether these should be split into per-process shifts.
2. CMS_res_m: no exact master entry seen in the fetched documentation
   excerpt, named by analogy with CMS_res_e.
3. CMS_scale_met_recoil_response / CMS_res_met_recoil_resolution: no
   exact master entry for recoil corrections specifically.
4. CMS_l1_ecal_prefiring{Up,Down}: assumed ECAL prefiring source; verify
   against the actual NanoAOD branch used (nanoAODv9.L1PreFiringWeight_Nom).
5. CMS_htt_zptReweight: analysis-specific uncertainty named without a
   known CADI id; convention strictly wants CMS_<analysisid>_...
6. jesUncHEMIssue -> CMS_scale_j_HEMIssue_2018: no master entry for this
   one-off 2018 detector issue.
7. DeepTau version tag for the >=2024 tau ID branch (vsJetDM{dm}pT{pt})
   could not be confirmed against producers/scalefactors.py; kept as
   DeepTau2018v2p5.
8. EleTauTriggerSF / MuTauTriggerSF / DoubleTauTriggerSF: renamed as
   combined "_cross" shifts since one add_shift call varies both trigger
   legs together; master's naming is really meant for the tau leg alone.
9. Four embedding-only trigger shifts in tau_triggersetup.py left
   unrenamed, see "NOT RENAMED" section above.

=== 2026-07-20 addendum: era-tag decorrelation pass ===

Follow-up pass on top of the renames above, adding an explicit per-era tag
to config.py shift `name`s for every uncertainty the relevant object
twiki (systematics_master.txt / Conventions / TauPOG Wiki / EGamma
Scales-and-Smearings) says must be treated as uncorrelated across eras/
years, but whose CROWN shift name did not previously embed `era` (so an
identically-named shift from every era's build_config() call would
otherwise collide into one accidentally-correlated nuisance downstream).
A new module-level `ERA_MAP` dict (config.py top) maps each era string to
the systematics_master.yml-style era token (e.g. "2022preEE" -> "2022",
"2022postEE" -> "2022EE", "2023postBPix" -> "2023BPix", matching the
tokens already used for jet_variations.py per the jets audit); this is
computed once per build_config() call as `era_tag = ERA_MAP[era]`.

Renamed (era_tag appended, shift_key/correction string unchanged unless
noted):
  muonEsScale        -> muonEsScale_{era_tag}
  muonEsReso         -> muonEsReso_{era_tag}
  eleEsReso          -> eleEsReso_{era_tag}   (both <2022 and >=2022 branches)
  eleEsScale         -> eleEsScale_{era_tag}  (both <2022 and >=2022 branches)
  zPtReweightWeight_unc{n} -> zPtReweightWeight_unc{n}_{era_tag}  (NNLO and
                              NLO/amcatnlo blocks; per-fit-parameter AND
                              per-era decorrelation, per user request --
                              AUDIT_REPORT_zpt.txt had left era-correlation
                              to the downstream combine/datacard stage,
                              this supersedes that and decorrelates at the
                              CROWN level instead)
  tauEsDM{dm}        -> tauEsDM{dm}_{era_tag}          (2022-2023 TES)
  tauEsDM{dm}pT{pt}  -> tauEsDM{dm}pT{pt}_{era_tag}    (>=2024 TES)
  tauEleFakeEsDM{dm}Barrel/Endcap -> ..._{era_tag}     (both era branches)
  tauMuFakeEsDM{dm}  -> tauMuFakeEsDM{dm}_{era_tag}    (both era branches)
  vsEleDM{dm}Barrel/Endcap (SF)   -> ..._{era_tag}
  vsMuWheel{wheel} (SF)           -> vsMuWheel{wheel}_{era_tag}
  vsJetStat1{era}DM{dm}    -> vsJetStat1{era_tag}DM{dm}   (era-string ->
  vsJetStat2{era}DM{dm}    -> vsJetStat2{era_tag}DM{dm}    era_tag, same
  vsJetSystTES{era}DM{dm}  -> vsJetSystTES{era_tag}DM{dm}  decorrelation,
  vsJetSyst{era}           -> vsJetSyst{era_tag}            just consistent
                                                             token style)

Rationale per family:
- muon/electron energy scale+resolution: EGamma "Scales_and_Smearings"
  doc and standard MUO/EGM practice treat per-era scale/smearing
  corrections as separate, uncorrelated measurements; nothing in either
  doc suggests correlating them across eras.
- Z pT reweighting: DY_kinematic_reweighting doc requires each
  fit-parameter uncertainty "fully uncorrelated from each other"; the
  per-era decorrelation is an explicit user request on top of that
  (each era's DY_pTll_reweighting fit is an independent measurement).
- Tau ES (genuine/e-fake/mu-fake) and e/mu-fake tau ID SF: TauPOG Wiki
  states explicitly "TES... decorrelated per era and DM bin", e-fake SF/ES
  "uncorrelated across Eras, as well as across Tau Eta and DM bins", and
  mu-fake SF "uncorrelated across years, as well as across tau eta bins" --
  none of these were previously era-tagged (only the vsJet ID SF from
  Issue #2 was). This pass extends the same era-tagging pattern used
  there to these families.
- vsJet ID SF (stat1/stat2/syst_TES) and CMS_res_m/CMS_res_e/CMS_scale_m/
  CMS_scale_e: already effectively decorrelated at the correctionlib-key
  level per era (era_key baked into the correction-string lookup itself);
  this pass only aligns the shift *name* token style to the new
  `era_tag`/ERA_MAP convention for consistency across the file (was
  previously the raw `era` string, e.g. "vsJetSyst2022preEE" ->
  "vsJetSyst2022").

Not changed / edge cases:
- btag, jet (JES/JER) shift names already embed era via their own
  per-topic ERA_MAP-equivalent (jet_variations.py, see original section
  above) -- left untouched, out of scope for this analysis-config-level
  pass (that file lives in the outer CROWN repo).
- Electron ID SF (CMS_eff_e_id / electronIdSF) and muon ID/Iso SF
  (muon_id_variation/muon_iso_variation, see the muon_sf_variation
  KeyError fix in a separate commit on this branch) currently have NO
  Up/Down shift wired at all in config.py (no add_shift call references
  them) -- there is nothing to era-tag; flagged as a pre-existing gap,
  not fixed here since adding a wholly new systematic is out of scope
  for a renaming/decorrelation pass.
- Trigger SF shifts (CMS_trig_*) and trigger filter-bit correctness are
  being handled in a separate, parallel worktree/pass -- not touched
  here to avoid stepping on that work.

=== 2026-07-20 follow-up: vsJet era-token reverted to out-of-scope ===

The addendum above (era-tag decorrelation pass) also changed
vsJetStat1{era}DM{dm}, vsJetStat2{era}DM{dm}, vsJetSystTES{era}DM{dm}, and
vsJetSyst{era} to use the mapped `era_tag` token instead of the raw `era`
string (e.g. "vsJetSyst2022postEE" -> "vsJetSyst2022EE"). That edit was
reverted in this pass: the task instructions for this branch explicitly
scope the vsJet SF shifts as "already era-tagged correctly by the prior
audit, out of scope here" (Issue #2 of AUDIT_REPORT_tau.txt), regardless
of whether a follow-on edit only touches token spelling rather than
correlation behavior. vsJetStat1/2, vsJetSystTES, and vsJetSyst therefore
go back to embedding the raw `era` string (e.g. "vsJetStat12022preEEDM0"),
matching Issue #2's original fix exactly. No functional change either way
(era and era_tag are both unique per era, so decorrelation is identical);
this is purely about respecting the stated scope boundary for this task.

Also, a small correction to the "NOT DONE / LEFT OPEN" note above: the
electronIdSF shift is NOT actually missing an add_shift wiring -- it has
one (config.py, scopes ("et","ee","em"), shift_key "ele_sf_variation",
shift_map {"Up":"sfup","Down":"sfdown"}), and it was correctly era-tagged
to electronIdSF_{era_tag} earlier in this same pass. The "no Up/Down shift
wired" gap applies only to muon_id_variation/muon_iso_variation (muon
ID/Iso SF): grepping config.py confirms no add_shift call, and no default
config parameter, ever sets "muon_id_variation" or "muon_iso_variation" --
so Muon_1/2_ID_SF and Muon_1/2_Iso_SF always evaluate at whatever
correctionlib "systematic" string default the C++ side falls back to,
with no Up/Down variation reachable from any shift name. This is a
pre-existing gap (unrelated to era-tagging) worth a separate follow-up,
not fixed here per the task's instruction not to invent new shifts.
